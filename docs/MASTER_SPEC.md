# Admission Forecast — Master Project Specification

## 1. Роль и цель

Ты — senior software engineer, data engineer и ML engineer. Разрабатывай систему прогнозирования поступления в российские вузы на основе исторических данных, текущих результатов ЕГЭ, прогнозируемого прогресса абитуриента и сценариев конкуренции.

Продукт: Telegram-бот, который позволяет абитуриенту:
- ввести текущие баллы пробников ЕГЭ;
- указать нагрузку и регулярность подготовки;
- добавить олимпиады и другие индивидуальные достижения;
- посмотреть вероятность достижения целевых баллов;
- оценить вероятность поступления на выбранные программы;
- сравнить программы и сценарии подготовки;
- отслеживать изменения данных и прогнозов во время приёмной кампании.

Главное требование: прогноз должен быть объяснимым, проверяемым и честно отражать неопределённость.

Не создавай видимость точности там, где нет данных.

## 2. Целевые университеты

Начальный каталог:
1. МФТИ.
2. НИУ ВШЭ.
3. ИТМО.
4. МИФИ.
5. СПбГУ.
6. МГУ.
7. НГУ.
8. МГТУ им. Баумана.
9. Университет Иннополис.
10. Центральный университет.

Охватывай программы бакалавриата и специалитета, относящиеся к:
- математике и прикладной математике;
- компьютерным и информационным наукам;
- информатике и вычислительной технике;
- программной инженерии;
- анализу данных;
- искусственному интеллекту и ML;
- релевантным смежным областям.

Не ограничивайся программами, в названии которых есть слова AI или ML. Классифицируй программы по официальному коду, описанию и направлению подготовки.

Не выдумывай список программ и не утверждай, что каталог полный, пока он не проверен.

## 3. Архитектура

Используй:
- TypeScript для Cloudflare Worker и основной бизнес-логики;
- Cloudflare Workers для Telegram webhook;
- Cloudflare D1 для SQL-хранилища;
- Python для сбора, нормализации, анализа и проверки данных;
- Git для версионирования кода, схем и обработанных датасетов;
- GitHub Actions только как дополнительную автоматизацию, а не как обязательный постоянно работающий сервер.

Целевой режим: бесплатное развёртывание без VPS, платных API, платных LLM и обязательного собственного домена.

Не запускай тяжёлый парсинг PDF, обучение моделей или массовые симуляции внутри Telegram webhook.

Модельные расчёты должны выполняться локально или офлайн. Worker использует компактные готовые параметры, вероятностные таблицы и лёгкие вычисления.

Не добавляй зависимости без необходимости.

## 4. Организация данных

Создай единый реестр источников. Для каждого источника храни:
- университет и URL;
- тип документа;
- годы, к которым относятся данные;
- дату последней проверки;
- способ извлечения;
- статус парсинга;
- ссылку на исходный материал;
- полноту и надёжность извлечённых данных;
- ошибки и замечания.

Приоритет источников:
1. Официальные страницы приёмных комиссий.
2. Официальные архивы, приказы и документы.
3. Официальная общая статистика приёма.
4. Сторонние агрегаторы только для поиска, сопоставления и проверки.

Не обходи авторизацию, CAPTCHA и технические ограничения источников.

Соблюдай разумную частоту запросов. Если парсер не может уверенно извлечь данные, сохраняй статус ошибки и отправляй запись на ручную проверку. Не подменяй отсутствующие значения нулями.

Для всех чисел сохраняй происхождение, год, единицу измерения и методику расчёта.

## 5. Модель данных

Разделяй следующие сущности:
- institutions;
- programs;
- program_versions;
- admission_years;
- admission_tracks;
- admission_rules;
- historical_metrics;
- score_distributions;
- source_records;
- model_versions;
- user_profiles;
- user_score_history;
- user_achievements;
- saved_programs;
- forecast_results.

У каждой программы должен быть стабильный внутренний ID. Название, код, кампус, структура экзаменов и правила могут меняться между годами.

Разделяй:
- общий бюджетный конкурс;
- отдельные квоты;
- целевой приём;
- БВИ;
- платное обучение;
- грантовые и специальные отборы.

Не смешивай их в одну общую вероятность.

Исторические записи не должны перезаписываться без сохранения происхождения и версии. Предусмотри исправления данных и повторный импорт.

Публичные сведения об абитуриентах не нужно без необходимости сохранять в индивидуальном виде. Для начала используй агрегаты и обезличенные наблюдения.

## 6. Аудит данных — первый приоритет

Прежде чем создавать сложную модель, реализуй аудит источников.

Для каждой программы и года проверь наличие:
- официального названия и кода;
- правил приёма;
- конкурсных экзаменов;
- бюджетных и платных мест;
- проходного и среднего балла;
- числа заявлений и зачисленных, если опубликовано;
- информации о БВИ и квотах;
- распределения баллов или конкурсных списков, если доступны;
- ссылки на первичный источник.

Сформируй DATA_AUDIT.md с таблицами по всем десяти университетам.

Отдельно укажи:
- число найденных программ;
- число программ с проверенными официальными источниками;
- количество доступных лет истории;
- долю заполненных обязательных полей;
- проблемы извлечения;
- какие программы можно прогнозировать, а какие пока нельзя;
- где требуется ручной сбор.

Не заявляй о полном аудите, если фактически проверена только часть программ.

## 7. Прогноз прогресса ЕГЭ v0

Пока нет собственного датасета индивидуального прогресса, используй конфигурируемую эвристическую модель.

Пользователь вводит:
- текущий балл по каждому предмету;
- дату и тип пробника;
- часы подготовки в неделю по предметам;
- регулярность подготовки;
- желаемые результаты;
- предполагаемую дату экзамена.

Прогнозируй результат по каждому предмету отдельно.

Прирост должен зависеть от текущего диапазона баллов, предмета, интенсивности подготовки и оставшегося времени. Учитывай ограничение в 100 баллов и уменьшение ожидаемого прироста вблизи верхней границы.

Целевой балл используется для расчёта необходимого прогресса и анализа сценариев. Само желание получить высокий балл не должно автоматически увеличивать прогноз.

Храни начальные параметры в конфигурации, а не в коде.

Не выдумывай эмпирические нормы месячного прироста. Явно обозначай начальные значения как предположения и добавляй широкую неопределённость.

Подготовь архитектуру, позволяющую позже заменить эвристики эмпирической моделью, обученной на добровольно собранных и обезличенных траекториях пробников и реальных ЕГЭ.

## 8. Прогноз поступления

Начни с простых базовых методов:
- проходной балл предыдущего года;
- историческое распределение проходных баллов;
- оценка изменения числа мест;
- сценарии изменения конкуренции и доли специальных категорий зачисления.

Для каждого направления храни вероятностную кривую поступления в зависимости от конкурсного балла. Её следует строить офлайн по историческим данным и сценариям, а не переобучать при каждом сообщении Telegram.

Вероятность поступления для пользователя объединяет:
1. распределение его будущих баллов ЕГЭ;
2. точный алгоритм расчёта конкурсного балла по правилам конкретной программы;
3. оценку вероятности зачисления при полученном конкурсном балле.

Правила зачисления должны быть отдельным детерминированным модулем. Не поручай ML-модели решать, какие олимпиады дают БВИ, какие экзамены требуются или как распределяются места.

Для программ с недостаточными данными:
- показывай исторические ориентиры;
- сообщай об отсутствии надёжного прогноза;
- не выдавай выдуманную точную вероятность.

Показывай базовый, оптимистичный и пессимистичный сценарии. Объясняй, какие предположения меняют результат.

## 9. Telegram-бот

Предусмотри команды:
- /start — регистрация и объяснение возможностей;
- /profile — профиль и текущие результаты;
- /programs — каталог программ;
- /search — поиск по вузу, направлению и условиям;
- /compare — сравнение выбранных программ;
- /forecast — прогноз ЕГЭ и поступления;
- /achievements — индивидуальные достижения;
- /sources — источники данных и дата обновления;
- /delete_data — удаление сохранённого пользовательского профиля.

Используй Telegram webhook через Cloudflare Worker.

Проверь секрет webhook. Храни токен бота только в секретах Cloudflare, не в исходном коде, конфигурациях с публичным доступом, тестовых данных или логах.

Не требуй загрузки сканов документов для работы первой версии. Начни со структурированного ввода достижений. Храни минимум персональных данных.

## 10. Бесплатный деплой

Подготовь:
- конфигурацию Worker;
- D1 migrations;
- инструкции создания базы;
- безопасную настройку секретов;
- команду локального запуска;
- команду тестового деплоя;
- инструкцию регистрации Telegram webhook;
- health endpoint;
- инструкцию обновления базы.

Учитывай лимит CPU бесплатного Worker. Не выполняй тяжёлые циклы симуляции на каждый запрос.

Используй индексы, подготовленные запросы и минимальное количество обращений к D1.

Не подключай платные сервисы как обязательную часть системы. Не требуй покупки домена. Не храни секреты в репозитории.

## 11. Тестирование

Обязательные тесты:
- валидация исходных данных;
- отсутствие отрицательных вероятностей;
- сумма вероятностей распределения равна единице;
- прогноз ЕГЭ не выходит за пределы 0–100;
- отсутствие роста результата выше 100;
- корректность расчёта конкурсных баллов;
- раздельная обработка категорий поступления;
- обработка отсутствующих и конфликтующих данных;
- воспроизводимость офлайн-расчётов;
- проверка SQL-миграций;
- тесты Telegram webhook;
- проверка отсутствия токенов и персональных данных в логах.

Создай искусственные тестовые данные, но маркируй их как synthetic. Никогда не выдавай их за реальные результаты приёма.

## 12. Этапы реализации

Работай небольшими этапами.

Этап 0:
- изучи существующий репозиторий;
- опиши архитектуру;
- создай структуру каталогов;
- создай схемы данных и конфигурации;
- создай документацию и базовые тесты.

Этап 1:
- собери реестр официальных источников;
- реализуй первые адаптеры извлечения;
- создай аудит программ и отчёт полноты данных.

Не переходи к массовой реализации ML, пока не завершён аудит источников и не понятны ограничения датасета.

После каждого этапа:
- запусти тесты;
- перечисли изменённые файлы;
- укажи проверенные результаты;
- перечисли нерешённые проблемы;
- сообщи, что осталось сделать.

Не переписывай весь репозиторий без необходимости. Сохраняй существующие полезные результаты.

## 13. Первый результат

Сейчас выполни только Этап 0 и подготовь основу для Этапа 1.

В конце представь:
1. Архитектуру проекта.
2. Дерево файлов.
3. Документацию.
4. Схему базы данных.
5. Результаты тестов.
6. Перечень официальных источников, которые будут проверяться на Этапе 1.
7. Список технических рисков.
8. Следующий конкретный шаг.

Не заявляй, что система уже умеет прогнозировать поступление, пока соответствующие модели и данные действительно не реализованы и не проверены.
